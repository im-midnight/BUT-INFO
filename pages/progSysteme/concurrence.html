Accès concurrents et blocages

Passe la souris surTouche les termes soulignés en pointillé pour afficher leur définition.

1. Le problème : deux goroutines, deux variables

Deux goroutines échangent un million de fois les valeurs de a et b. Un nombre pair d'échanges devrait toujours redonner 1 2.

var a, b = 1, 2

func echanger(wg *sync.WaitGroup) {
	for i := 0; i < 1000000; i++ {
		a, b = b, a
	}
	wg.Done()
}

func main() {
	var wg sync.WaitGroup
	wg.Add(2)
	go echanger(&wg)
	go echanger(&wg)
	wg.Wait() // attend que les deux goroutines aient fini
	fmt.Println(a, b)
}

Sur huit exécutions, on a obtenu 1 2 seulement trois fois. Les autres fois, c'était 1 1 ou 2 2 : une des deux valeurs a disparu. Sur une autre série, 2 1 est aussi sorti. Le résultat change à chaque lancement.

Ce qui s'est passé :

  • les deux goroutines modifient les mêmes variables en même temps ;
  • en concurrence, on ne peut faire aucune hypothèse sur l'ordre des instructions ;
  • l'échange a, b = b, a tient sur une ligne, mais il n'est pas atomique : il se fait en plusieurs étapes.

2. Pourquoi : les entrelacements

Une fois compilé, un échange ressemble à trois instructions, avec une variable temporaire propre à chaque goroutine :

1. t = a
2. a = b
3. b = t

Avec deux goroutines A et B qui font chacune un échange en partant de a = 1 et b = 2, il y a 20 façons d'entrelacer leurs 6 instructions. Elles ne donnent pas toutes le même résultat :

Résultat (a, b)Nombre d'entrelacementsUn exemple d'ordre
(1, 2) : les deux échanges ont eu lieu4A A A B B B (l'un après l'autre)
(2, 1) : un seul échange compte10A B A B A B
(1, 1) : la valeur 2 est perdue4A B A A B B
(2, 2) : la valeur 1 est perdue2A A B B A B

Prenons A B A A B B : A lit a (tA = 1), B lit a (tB = 1), A écrit a = 2 puis b = 1, B écrit a = b = 1 puis b = tB = 1. Résultat : 1 1.

On parle d'accès concurrents (race condition) quand plusieurs accès à une même variable, dont au moins une écriture, se font de façon concurrente.

Ajouter des time.Sleep ne règle rien : le bug devient plus rare, donc plus difficile à trouver, mais il est toujours là.

Go sait détecter ces accès : go run -race fichier.go. Sur l'exemple, il affiche WARNING: DATA RACE, même les fois où le résultat a l'air juste.

3. Section critique et exclusion mutuelle

  • Section critique : l'endroit du code où on accède à une ressource partagée. Ici, la ligne a, b = b, a.
  • Exclusion mutuelle : garantir qu'un seul fil d'exécution à la fois est dans la section critique. Il n'y a alors plus d'accès concurrents à la ressource.

Première idée : un drapeau

On attend que la place soit libre, on la marque comme prise, on fait l'échange, puis on la libère.

var occupe bool

for occupe {
	// on attend que la place se libère
}
occupe = true
a, b = b, a
occupe = false

Ça ne marche pas : on retrouve 1 1, 2 2… Les deux goroutines peuvent voir occupe == false au même moment, sortir toutes les deux de la boucle, et entrer ensemble dans la section critique. Tester le drapeau puis le modifier, ce sont deux opérations séparées, entre lesquelles l'autre goroutine peut passer.

La solution : une opération atomique

Si on sait tester une variable et changer sa valeur en une seule opération atomique, le problème est réglé. En Go, le paquet sync/atomic fournit CompareAndSwap : « si la valeur vaut 0, mets-la à 1 », sans que personne puisse passer entre les deux.

var occupe int32 // 0 : libre, 1 : pris

func prendre() {
	for !atomic.CompareAndSwapInt32(&occupe, 0, 1) {
		// la section est prise : on réessaie
	}
}

func rendre() {
	atomic.StoreInt32(&occupe, 0)
}

Avec prendre() avant l'échange et rendre() après, on obtient 1 2 à chaque fois.

4. La famine

Si chaque goroutine veut entrer plusieurs fois dans la section critique, rien ne garantit que chacune aura son tour. Une goroutine peut demander l'accès et ne jamais l'obtenir, simplement parce qu'une autre le redemande toujours au même moment. C'est la famine (starvation).

Une façon de s'en sortir est d'imposer un ordre de passage, par exemple chacun son tour selon son numéro. Mais cette solution est lente, et elle suppose que les goroutines démarrent dans l'ordre de leurs numéros : si celle dont c'est le tour n'est pas encore lancée, toutes les autres l'attendent.

5. Les sémaphores

Un sémaphore règle les deux problèmes, accès concurrents et famine. Il contient :

  • un compteur K, initialisé à 1 ;
  • une file d'attente de fils d'exécution, servie dans l'ordre d'arrivée (FIFO).

On l'utilise avec deux opérations :

OpérationCe qu'elle fait
P (réserver)K = K − 1. Si K < 0, le fil qui appelle est mis dans la file d'attente. Si K ≥ 0, il continue.
V (libérer)K = K + 1. Si K ≤ 0, le fil en tête de la file d'attente repart.

Comme la file est servie dans l'ordre, chaque fil finit par passer : plus de famine.

Un sémaphore peut aussi compter des ressources : K peut démarrer à plus que 1 (par exemple 3 places disponibles), et P ou V peuvent faire varier K de plus de 1.

En Go : sync.Mutex

Le paquet sync fournit le type Mutex, qui correspond à peu près à un sémaphore avec K = 1 (sa file d'attente est gérée de façon plus complexe). Lock() joue le rôle de P, Unlock() celui de V.

var verrou sync.Mutex

func echanger(wg *sync.WaitGroup) {
	for i := 0; i < 1000000; i++ {
		verrou.Lock()
		a, b = b, a
		verrou.Unlock()
	}
	wg.Done()
}

Résultat : 1 2 à chaque exécution, et go run -race ne signale plus rien.

6. Les erreurs classiques avec les verrous

Ces synchronisations sont une source d'erreurs fréquente, et ça empire avec le nombre de ressources partagées. Les erreurs à surveiller :

  • se servir d'une ressource après l'avoir libérée ;
  • libérer une ressource sans l'avoir réservée ;
  • se servir d'une ressource sans l'avoir réservée ;
  • garder une ressource trop longtemps : les autres attendent pour rien ;
  • oublier de libérer une ressource : les autres attendent pour toujours.

Pour ne pas oublier de libérer, on écrit souvent defer verrou.Unlock() juste après verrou.Lock() : le verrou est rendu automatiquement à la fin de la fonction.

7. L'interblocage (deadlock)

Il y a interblocage quand tous les fils d'exécution sont bloqués en même temps : le programme ne peut plus avancer et n'a aucune chance de se débloquer.

Le risque apparaît surtout quand plusieurs mécanismes de synchronisation sont utilisés ensemble :

  • plusieurs ressources partagées, chacune protégée par son propre verrou ;
  • une ressource partagée et une lecture dans un canal ;
  • une ressource partagée et l'attente d'un évènement.

Exemple avec deux verrous pris dans un ordre différent :

var v1, v2 sync.Mutex

func f(premier, second *sync.Mutex, nom string, wg *sync.WaitGroup) {
	premier.Lock()
	time.Sleep(10 * time.Millisecond)
	second.Lock()
	fmt.Println(nom, "a les deux verrous")
	second.Unlock()
	premier.Unlock()
	wg.Done()
}

func main() {
	var wg sync.WaitGroup
	wg.Add(2)
	go f(&v1, &v2, "A", &wg) // A prend v1, puis veut v2
	go f(&v2, &v1, "B", &wg) // B prend v2, puis veut v1
	wg.Wait()
}

A attend que B rende v2, et B attend que A rende v1. Personne ne rend rien. Go s'en aperçoit et arrête le programme :

fatal error: all goroutines are asleep - deadlock!

Si tous les fils prennent les verrous dans le même ordre (toujours v1 avant v2), cet interblocage ne peut pas arriver.

8. Et les map de Go ?

Une map Go n'est pas protégée contre les accès concurrents. Deux goroutines qui écrivent dedans en même temps, sans verrou :

m := make(map[int]int)
for g := 0; g < 2; g++ {
	go func() {
		for i := 0; i < 100000; i++ {
			m[i] = i
		}
	}()
}

Cette fois, Go repère l'écriture simultanée et arrête le programme :

fatal error: concurrent map writes

Comme pour les variables, il faut protéger les accès à la map avec un sync.Mutex.

Accès concurrents (race condition)

Plusieurs fils d'exécution accèdent à la même variable en même temps, et au moins un l'écrit. Le résultat dépend alors de l'ordre, qu'on ne contrôle pas.

Opération atomique

Une opération qui se fait d'un seul bloc : aucun autre fil ne peut passer au milieu.

  • a, b = b, a n'est pas atomique : c'est plusieurs lectures et écritures.

Section critique

Le morceau de code qui touche à une ressource partagée. Un seul fil à la fois doit pouvoir s'y trouver.

Exclusion mutuelle

Garantir qu'un seul fil d'exécution à la fois est dans la section critique. Les autres attendent leur tour.

Famine (starvation)

Un fil demande l'accès à une ressource et ne l'obtient jamais, parce que d'autres passent toujours avant lui.

Sémaphore

Un compteur et une file d'attente. P réserve (et met en attente s'il n'y a plus de place), V libère (et réveille le premier de la file).

Interblocage (deadlock)

Tous les fils d'exécution sont bloqués en même temps, chacun attend un autre : le programme ne peut plus avancer.
