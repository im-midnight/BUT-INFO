JPA (Jakarta Persistence API)

Passe la souris surTouche les termes soulignés en pointillé pour afficher leur définition.

1. Persistance, JDBC et approche ORM

La persistance consiste à sauvegarder des données durablement (après l'arrêt du serveur), le plus souvent dans un SGBD relationnel (PostgreSQL, MySQL, H2...).

Problème : deux mondes s'opposent. En Java (POO), on manipule des objets liés entre eux, qui cachent leurs attributs et exposent des méthodes. Dans une base SQL, on stocke des lignes dans des tables reliées par des clés étrangères.

ApprocheNiveauPoints fortsLimites
JDBCBas niveauTrès performant, contrôle total du SQL.Verbeux (connexions, PreparedStatement, mapping manuel), dépend parfois du dialecte SQL.
JPA (ORM)Haut niveauConcis, on manipule des objets Java, très portable d'un SGBD à l'autre.Légèrement plus lent, nécessite de comprendre le chargement des relations.

JPA n'est pas une bibliothèque, mais une spécification (un ensemble d'interfaces et d'annotations dans jakarta.persistence). Pour l'exécuter, il faut une implémentation : la plus connue est Hibernate (devant EclipseLink ou OpenJPA).

JPA repose sur 3 piliers : les entités annotées, l'API EntityManager pour le CRUD, et le langage de requête objet JPQL.

2. Architecture et configuration (persistence.xml)

En JPA standard (hors Spring Boot), toute la configuration de la base est décrite dans une unité de persistance placée dans src/main/resources/META-INF/persistence.xml. La chaîne d'objets au démarrage est toujours la même :

  1. Persistence lit persistence.xml et construit une EntityManagerFactory (lourde : créée une seule fois pour toute l'application).
  2. L'EntityManagerFactory fabrique des EntityManager (légers : un par traitement/requête).
  3. L'EntityManager gère les entités, ouvre des transactions (EntityTransaction) et exécute des requêtes (TypedQuery).
<persistence xmlns="https://jakarta.ee/xml/ns/persistence" version="3.0">
  <persistence-unit name="myPersistenceUnit">
    <provider>org.hibernate.jpa.HibernatePersistenceProvider</provider>
    <class>iut.nantes.entities.Product</class>
    <properties>
      <property name="jakarta.persistence.jdbc.driver" value="org.h2.Driver"/>
      <property name="jakarta.persistence.jdbc.url" value="jdbc:h2:mem:test"/>
      <property name="jakarta.persistence.jdbc.user" value="sa"/>
      <property name="jakarta.persistence.jdbc.password" value=""/>
      <property name="hibernate.hbm2ddl.auto" value="update"/>
      <property name="hibernate.show_sql" value="true"/>
    </properties>
  </persistence-unit>
</persistence>

La propriété hibernate.hbm2ddl.auto contrôle la génération des tables depuis tes classes Java : create (recrée tout à chaque démarrage, pratique en test), update (met à jour le schéma), validate (vérifie sans rien modifier, recommandé en production).

3. Définir une Entité JPA

Une entité est une classe Java dont chaque instance correspond à une ligne dans une table SQL. Deux règles sont obligatoires : annoter la classe avec @Entity, définir une clé primaire avec @Id, et fournir un constructeur sans paramètre (pour qu'Hibernate puisse reconstruire l'objet depuis la base).

@Entity
@Table(name = "STUDENT")
public class Student {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "STUDENT_NAME", length = 50, nullable = false, unique = false)
    private String name;

    @Transient // Non enregistré en base (ex: valeur calculée en mémoire)
    private Integer age;

    @Temporal(TemporalType.DATE) // Pour java.util.Date (inutile avec LocalDate)
    private Date birthDate;

    @Enumerated(EnumType.STRING) // Stocke "CDI" au lieu de l'index 0, 1, 2
    private StatutContrat statut;

    public Student() {} // Constructeur vide obligatoire pour JPA
    // Getters et setters...
}

Piège classique sur @Enumerated : par défaut, JPA utilise EnumType.ORDINAL et stocke la position numérique (0, 1, 2) de l'énumération. Si tu ajoutes une valeur au milieu de ton enum, toutes les anciennes lignes de la base deviennent fausses ! Utilise toujours @Enumerated(EnumType.STRING).

4. Les relations (cardinalités) et Lazy vs Eager

JPA traduit les liens entre classes Java en clés étrangères et tables de jointure. Sur une relation bidirectionnelle, un côté est le propriétaire (il porte @JoinColumn ou @JoinTable, c'est lui qui met à jour la clé étrangère en base) et l'autre côté est le miroir avec mappedBy.

CardinalitéAnnotationsTraduction en base SQL
1 — 1@OneToOne + @JoinColumnUne clé étrangère unique dans l'une des tables (ou partage de clé primaire).
1 — N / N — 1@OneToMany(mappedBy="...") et @ManyToOneLa clé étrangère se trouve toujours du côté N (@ManyToOne).
N — N@ManyToMany + @JoinTableUne table d'association contenant les deux clés étrangères.

Exemple 1 — N : un Département contient plusieurs Employés

@Entity
public class Department {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;

    // Côté inverse (miroir) : le champ "department" dans Employee porte la clé étrangère
    @OneToMany(mappedBy = "department", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Employee> employees = new ArrayList<>();
}

@Entity
public class Employee {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;

    // Côté propriétaire : crée la colonne department_id dans la table EMPLOYEE
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")
    private Department department;
}

Cas spécial : relation N — N avec attribut (ex. une note rating)

En JPA, @ManyToMany ne peut pas porter d'attribut supplémentaire sur la table de jointure. On la transforme alors en une entité intermédiaire (ex. CourseRating) reliée par deux @ManyToOne, avec une clé primaire composite (@Embeddable + @EmbeddedId + @MapsId).

Chargement LAZY vs EAGER

  • FetchType.LAZY (paresseux) : les objets liés ne sont chargés depuis la base qu'au moment où tu appelles réellement leur getter (ex. dept.getEmployees()). C'est le défaut sur @OneToMany et @ManyToMany — meilleur pour les performances.
  • FetchType.EAGER (immédiat) : tout est chargé en une fois en même temps que l'entité principale. Défaut sur @ManyToOne et @OneToOne — à éviter sur les collections sous peine de charger la moitié de la base à chaque requête.

L'option cascade = CascadeType.ALL propage automatiquement les opérations (persistance, suppression) du parent vers ses enfants ; orphanRemoval = true supprime en base un enfant retiré de la liste.

5. Manipuler les données : EntityManager et JPQL

L'EntityManager est la passerelle entre tes objets Java et la base. Il suit le cycle de vie de chaque entité (nouvelle, gérée, détachée ou supprimée). Toute opération d'écriture (ajout, modification, suppression) doit se faire dans une transaction.

EntityManagerFactory emf = Persistence.createEntityManagerFactory("myPersistenceUnit");
EntityManager em = emf.createEntityManager();

// 1. CREATE, UPDATE et DELETE dans une transaction
em.getTransaction().begin();

Product p1 = new Product("Clavier", 35.0, 20);
em.persist(p1);                     // INSERT : p1 devient "gérée" (managed)

p1.setPrice(29.9);                  // UPDATE automatique au commit (dirty checking)

Product aSupprimer = em.find(Product.class, 2L);
if (aSupprimer != null) {
    em.remove(aSupprimer);          // DELETE
}

em.getTransaction().commit();       // Envoie réellement le SQL à la base

// 2. READ : par clé primaire ou par requête JPQL
Product p = em.find(Product.class, 1L);

TypedQuery<Product> query = em.createQuery(
    "SELECT p FROM Product p WHERE p.price <= :max", Product.class);
query.setParameter("max", 50.0);
List<Product> pasChers = query.getResultList();

em.close();

Ne confonds pas SQL et JPQL : en JPQL, on écrit le nom de la classe Java (Product, sensible à la casse) et de ses attributs Java (p.price), jamais les noms des tables ou colonnes SQL ! Utilise toujours des paramètres nommés (:max) et jamais de concaténation de chaînes pour éviter les injections SQL.

Persistance des données

Le fait de conserver les données sur un support durable (comme une base de données) afin qu'elles ne disparaissent pas quand le programme s'arrête.

SGBD relationnel (SGBD-R)

Un logiciel qui stocke les données sous forme de tables (lignes et colonnes) reliées entre elles, interrogées avec SQL (ex. PostgreSQL, MySQL, H2).

JDBC (Java Database Connectivity)

L'interface Java de base pour envoyer directement des requêtes SQL à une base de données et lire les résultats colonne par colonne.

ORM (Object-Relational Mapping)

Un traducteur automatique entre tes objets Java et les tables SQL : il écrit les requêtes INSERT, SELECT, UPDATE et DELETE à ta place.

JPA (Jakarta Persistence API)

Le standard officiel de Java pour faire de l'ORM grâce à des annotations (@Entity, @Id...) et une API unifiée.

Spécification

Un cahier des charges officiel qui définit les noms des classes, interfaces et annotations, sans fournir le moteur interne. Plusieurs outils peuvent l'implémenter (comme Hibernate).

Hibernate

L'implémentation la plus utilisée de JPA : c'est le moteur concret qui génère le SQL et dialogue avec la base de données en coulisses.

JPQL (Jakarta Persistence Query Language)

Un langage de requête qui ressemble à SQL, mais qui interroge tes classes et attributs Java au lieu des tables de la base. Hibernate le traduit ensuite dans le bon SQL.

Unité de persistance (Persistence Unit)

Un bloc de configuration dans persistence.xml qui regroupe une base de données, ses identifiants de connexion et la liste des entités JPA à gérer.

Transaction

Un bloc d'opérations en base qui fonctionne en « tout ou rien » : si tout réussit, on valide (commit) ; en cas d'erreur, on annule tout (rollback) pour garder la base cohérente.

Entité JPA

Une classe Java annotée @Entity qui représente une table de la base de données. Chaque objet créé à partir de cette classe correspond à une ligne de la table.

Clé primaire composite

Une clé primaire formée en combinant plusieurs colonnes ensemble (ex. student_id + course_id pour identifier de façon unique la note d'un étudiant à un cours).

Chargement LAZY vs EAGER

Deux stratégies pour charger les données liées : LAZY attend que ton code demande la relation pour lancer le SELECT ; EAGER récupère tout immédiatement dès le départ.

EntityManager

L'objet principal de JPA qui joue le rôle de chef d'orchestre : c'est sur lui qu'on appelle persist, find, remove et createQuery.

Injection SQL

Une attaque où un utilisateur malveillant saisit des morceaux de code SQL dans un champ (ex. ' OR 1=1--) pour détourner une requête construite par concaténation.
